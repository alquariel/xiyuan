# AFP ABB C++ Slice J Design: DDS Pressure Archive To InfluxDB

Date: 2026-05-27

## Goal

Add a new optional time-series archive workflow to the C++ application.

When `AFP_ABB_CPP.exe` starts, it can automatically start an eProsima Fast DDS subscriber process. That subscriber will read the existing pressure sensor DDS stream and write the data into InfluxDB 3 Core in real time.

This slice is intentionally a new feature. It was not part of the original Python software. The pressure acquisition and publishing behavior from Slice C remains unchanged, and the Python source remains read-only.

The subscriber will also support optional live console printing so the user can watch incoming pressure samples in a command window during tests.

## Source And Runtime Context

The pressure data already exists as a DDS topic from Slice C.

Current pressure DDS fields are defined by `src/pressure/PressureSample.idl`:

- `timestamp_ms`
- `sequence`
- `raw_value`
- `mean_value`
- `variance_value`
- `standard_deviation_value`
- `peak_value`
- `window_ready`
- `sensor_running`

The existing pressure config already contains:

```json
"pressure": {
  "dds_domain_id": 0,
  "dds_topic": "afp.pressure.sample"
}
```

InfluxDB 3 Core is installed outside the portable C++ application folder. The default executable path for this workstation is:

```text
D:/InfluxDB 3 Core/influxdb3-core-3.9.2-windows_amd64/influxdb3.exe
```

The offline preconfigured admin token file has already been generated by the user as:

```text
D:/InfluxDB 3 Core/afp-admin-token.json
```

## Scope

Slice J includes:

- A new DDS subscriber executable, separate from the Qt main application.
- A pressure DDS reader that subscribes to `PressureSample`.
- A reusable time-series point model used by all current and future DDS readers.
- A single InfluxDB line-protocol writer that can accept points from multiple readers.
- Optional automatic startup of InfluxDB 3 Core.
- Optional database existence check and create-on-missing behavior.
- Optional automatic startup of the DDS subscriber when `AFP_ABB_CPP.exe` starts.
- Optional live console output from the subscriber.
- User config fields for all paths, connection settings, database names, topics, batching, and console behavior.
- README instructions for generating the offline preconfigured admin token file, starting InfluxDB manually, and validating writes after implementation.

Slice J excludes:

- Any Qt UI redesign.
- Any changes to pressure sensor acquisition.
- Any changes to the pressure DDS publisher format.
- Any storage of images or camera frames.
- Any robot, PLC, FTP, high-speed camera, or thermal camera workflow change.
- Any hardcoded secret token in C++ source code.
- Any requirement that InfluxDB be bundled into the portable `AFP_ABB_CPP.exe` release folder.

## Architecture

The archive workflow uses a separate process instead of embedding database writes directly in the main Qt application.

```text
AFP_ABB_CPP.exe
  |
  | optional start
  v
influxdb3.exe
  |
  | HTTP write API
  ^
  |
dds_influx_subscriber.exe
  |
  | Fast DDS subscribe
  ^
  |
PressureDdsPublisher inside AFP_ABB_CPP.exe
```

This separation keeps the main UI responsive and keeps database failures away from the robot, PLC, camera, and pressure control paths. If the archive process fails, the main application can report the failure without terminating the AFP workflow.

## Subscriber Components

### `DdsInfluxSubscriberApp`

`DdsInfluxSubscriberApp` is the command-line entry point for the archive process.

Responsibilities:

- Load the same runtime config format used by the main application.
- Create the configured DDS readers.
- Create one shared InfluxDB writer.
- Optionally create a console printer.
- Run until the process receives a stop request.
- Flush any buffered points before shutdown.

### `IDdsTimeSeriesReader`

`IDdsTimeSeriesReader` is the common interface for DDS readers that can produce time-series points.

Responsibilities:

- Start and stop one DDS subscription.
- Convert incoming DDS samples into a common `TimeSeriesPoint` structure.
- Report connection and subscription errors in plain text.

The first implementation will be `PressureSampleReader`.

Future readers, such as `FutureReaderA` and `FutureReaderB`, do not need their own database writer. They only need to convert their DDS-specific samples into `TimeSeriesPoint` values. The same `InfluxLineProtocolWriter` can write all points from all readers.

### `PressureSampleReader`

`PressureSampleReader` subscribes to the configured pressure DDS topic and converts every `PressureSample` into one InfluxDB point.

Default table:

```text
pressure_sensor
```

Default tag:

```text
source=pressure_sensor_1
```

Fields:

- `raw_value`
- `mean_value`
- `variance_value`
- `standard_deviation_value`
- `peak_value`
- `sequence`
- `window_ready`
- `sensor_running`

Timestamp:

- The DDS `timestamp_ms` value converted to nanoseconds for InfluxDB line protocol precision.

### `TimeSeriesPoint`

`TimeSeriesPoint` is a small internal data structure shared by all readers and writers.

It will contain:

- table name
- tags
- numeric fields
- boolean fields
- integer fields
- timestamp in nanoseconds

This avoids coupling the InfluxDB writer directly to `PressureSample`. It also makes future readers easier to add.

### `InfluxLineProtocolWriter`

`InfluxLineProtocolWriter` is the only database writer required for this slice.

Responsibilities:

- Accept `TimeSeriesPoint` values from any reader.
- Convert points into InfluxDB line protocol.
- Buffer points in memory.
- Flush the buffer when either:
  - `write_batch_size` points are queued, or
  - `write_flush_interval_ms` has elapsed.
- Send writes to the configured InfluxDB HTTP endpoint.
- Include the admin token from the configured token file in write requests.
- Report write failures without crashing the main Qt process.

The default `write_batch_size` will be `10`. This is intentionally lower than the earlier draft value of `100` because the user wants pressure storage to feel more real-time during testing.

A smaller batch size reduces buffering latency, but it can increase HTTP request frequency. With pressure samples arriving about every 100 ms, a batch size of `10` means the writer will normally send about once per second. The `write_flush_interval_ms` setting still matters because it forces a write even when fewer than 10 points arrive.

### `ConsolePrinter`

`ConsolePrinter` is optional.

When enabled, the subscriber process will show a command window and print a compact live line for each pressure sample or flush cycle.

When disabled, the subscriber should still run in the background. The main application can report whether it started successfully, but no live console window is required.

## InfluxDB Startup And Database Handling

InfluxDB startup has three separate concerns:

1. Start the InfluxDB server process with `influxdb3 serve`.
2. Wait until the HTTP endpoint is reachable.
3. Ensure the target database exists by calling the `influxdb3` CLI.

All three can be automated when `AFP_ABB_CPP.exe` starts if enabled in config.

If `timeseries_archive.start_influxdb` is `true`, the main application should first check whether `timeseries_archive.host_url` is already reachable. If it is reachable, the app should use that existing InfluxDB server and should not start another server on the same port.

If the endpoint is not reachable, the main application should start the configured InfluxDB executable with explicit server settings:

```powershell
influxdb3.exe serve `
  --node-id afp-node `
  --object-store file `
  --data-dir "D:\InfluxDB 3 Core\data" `
  --admin-token-file "D:\InfluxDB 3 Core\afp-admin-token.json"
```

The implementation should build this command from config values, not from hardcoded paths.

The config key should be named:

```json
"ensure_database_on_start": true
```

This means "create the database only if it does not already exist." It must not mean "replace the database every time." If `afp_process` already exists, the startup check should leave the existing database and existing data untouched.

Database ensure/create should use the `influxdb3` CLI instead of a hand-coded database-admin HTTP request. The recommended sequence is:

1. Read the token from `timeseries_archive.admin_token_file`.
2. Run `influxdb3 show databases --format json` with `INFLUXDB3_AUTH_TOKEN` and `INFLUXDB3_HOST_URL` set in the child process environment.
3. Check whether `timeseries_archive.database` is already listed.
4. If the database is missing, run `influxdb3 create database --retention-period <retention_period> <database>`.

For example, the create command is equivalent to:

```powershell
influxdb3 create database `
  --host http://localhost:8181 `
  --token <AUTH_TOKEN> `
  --retention-period 30d `
  afp_process
```

However, the implementation should prefer passing the token through the child process environment instead of placing the token directly on the command line:

```powershell
$env:INFLUXDB3_HOST_URL = "http://localhost:8181"
$env:INFLUXDB3_AUTH_TOKEN = "<AUTH_TOKEN>"
influxdb3 create database --retention-period 30d afp_process
```

The CLI method is chosen for startup database administration because it is official, easy to reproduce manually during troubleshooting, and avoids embedding extra database-admin HTTP endpoint details in the C++ code. Real-time pressure writes should still use the HTTP line-protocol write endpoint because that path is better suited to repeated batched data writes.

The default database name will be:

```text
afp_process
```

The retention period is only applied when the database is first created. If the database already exists, changing the retention setting in config should not be expected to modify the existing database.

## Admin Token Handling

The application must not hardcode the InfluxDB admin token.

The default config will point to the user-generated offline preconfigured token file:

```text
D:/InfluxDB 3 Core/afp-admin-token.json
```

The implementation should read the token from that JSON file. The JSON can contain the token field plus optional metadata, for example:

```json
{
  "token": "apiv3_your_secure_token_here",
  "name": "afp-admin",
  "description": "Admin token for AFP_ABB_CPP automatic InfluxDB startup"
}
```

InfluxDB-generated token files may include different optional fields, such as expiry metadata. The implementation should require only the `token` field.

README instructions at the end of Slice J implementation must explain how to generate the token file, using the user's filename:

```powershell
.\influxdb3.exe create token --admin `
  --name afp-admin `
  --offline `
  --output-file "D:\InfluxDB 3 Core\afp-admin-token.json"
```

The README must also explain that this file should be protected because it grants administrative access to the local InfluxDB instance.

## Proposed Config

The C++ config file should add a new `timeseries_archive` section:

```json
"timeseries_archive": {
  "enabled": true,
  "start_influxdb": true,
  "influxdb_exe_path": "D:/InfluxDB 3 Core/influxdb3-core-3.9.2-windows_amd64/influxdb3.exe",
  "host_url": "http://localhost:8181",
  "node_id": "afp-node",
  "object_store": "file",
  "data_dir": "D:/InfluxDB 3 Core/data",
  "admin_token_file": "D:/InfluxDB 3 Core/afp-admin-token.json",
  "database": "afp_process",
  "retention_period": "30d",
  "ensure_database_on_start": true,
  "subscriber_autostart": true,
  "subscriber_show_console": true,
  "subscriber_print_live_data": true,
  "write_batch_size": 10,
  "write_flush_interval_ms": 1000
}
```

Pressure-specific archive settings should stay separate:

```json
"pressure_archive": {
  "enabled": true,
  "dds_domain_id": 0,
  "dds_topic": "afp.pressure.sample",
  "table": "pressure_sensor",
  "source_tag": "pressure_sensor_1"
}
```

Config meanings:

- `timeseries_archive.enabled`: master switch for the archive feature.
- `timeseries_archive.start_influxdb`: whether the main app should start `influxdb3.exe`.
- `timeseries_archive.influxdb_exe_path`: path to the InfluxDB 3 Core executable.
- `timeseries_archive.host_url`: InfluxDB server URL used by CLI database checks and HTTP data writes.
- `timeseries_archive.node_id`: InfluxDB node identifier used by `influxdb3 serve`.
- `timeseries_archive.object_store`: InfluxDB object store mode, defaulting to `file`.
- `timeseries_archive.data_dir`: local InfluxDB data directory.
- `timeseries_archive.admin_token_file`: JSON file containing the admin token.
- `timeseries_archive.database`: target database name.
- `timeseries_archive.retention_period`: retention period used only when creating the database.
- `timeseries_archive.ensure_database_on_start`: create the database if it is missing.
- `timeseries_archive.subscriber_autostart`: whether the main app starts the subscriber process.
- `timeseries_archive.subscriber_show_console`: whether the subscriber process gets a visible console window.
- `timeseries_archive.subscriber_print_live_data`: whether incoming samples are printed.
- `timeseries_archive.write_batch_size`: number of points to buffer before writing.
- `timeseries_archive.write_flush_interval_ms`: maximum time to wait before flushing a partial batch.
- `pressure_archive.enabled`: whether pressure DDS data is archived.
- `pressure_archive.dds_domain_id`: DDS domain for the pressure subscriber.
- `pressure_archive.dds_topic`: DDS topic for pressure samples.
- `pressure_archive.table`: InfluxDB table name for pressure samples.
- `pressure_archive.source_tag`: stable source identifier stored with every pressure point.

## Data Format

The default pressure line protocol format will be:

```text
pressure_sensor,source=pressure_sensor_1 raw_value=12.3,mean_value=12.0,variance_value=0.1,standard_deviation_value=0.316,peak_value=12.8,sequence=42i,window_ready=true,sensor_running=true 1710000000000000000
```

The `source` tag identifies where the data came from. It is useful when more sensors or data streams are added later.

Tags should be stable and low-cardinality. Good values are names such as `pressure_sensor_1`, `thermal_camera_1`, or `plc_state`. Values that change every sample, such as timestamps or sequence numbers, must stay as fields rather than tags.

## Error Handling

Startup errors should be specific enough to diagnose the failing layer:

- InfluxDB executable path does not exist.
- InfluxDB process failed to start.
- InfluxDB HTTP endpoint did not become reachable before timeout.
- Admin token file does not exist.
- Admin token file is missing the required `token` field.
- Database ensure step failed.
- DDS participant creation failed.
- DDS topic subscription failed.
- DDS data is being received but InfluxDB writes are failing.

The main Qt application should display concise startup status messages. The subscriber console can print more detailed diagnostics when enabled.

## Process Lifetime

The main application may start two child processes:

- `influxdb3.exe`
- `dds_influx_subscriber.exe`

The implementation should avoid killing an existing user-started InfluxDB instance. If the configured host URL is already reachable, the main app should use it rather than starting another server on the same port.

When `AFP_ABB_CPP.exe` exits, it should stop the subscriber process it started. Whether it stops InfluxDB should be configurable or conservative. The safest default is to leave InfluxDB running if it may have been started outside the main app.

## Build And Portable Release

`dds_influx_subscriber.exe` should be built by the same CMake project.

The Release folder should contain:

```text
build/Release/AFP_ABB_CPP.exe
build/Release/dds_influx_subscriber.exe
build/Release/config/env_config.json
build/Release/lib/...
```

InfluxDB itself does not need to be copied into the portable AFP release folder for this slice because the user already has it installed in `D:/InfluxDB 3 Core/...`. The path remains configurable.

## Testing Plan

Hardware-free tests should cover:

- Config parsing for `timeseries_archive` and `pressure_archive`.
- Token JSON parsing using `afp-admin-token.json`-style content.
- Pressure `PressureSample` to `TimeSeriesPoint` conversion.
- Line protocol escaping and formatting.
- Batch flushing when `write_batch_size` is reached.
- Timer flushing when `write_flush_interval_ms` elapses.
- Disabled archive settings do not launch external processes.
- Missing token file reports a clear error.
- Missing `token` field reports a clear error.

Manual integration tests should cover:

1. Start InfluxDB with the configured token file.
2. Ensure the `afp_process` database exists.
3. Start `AFP_ABB_CPP.exe`.
4. Start pressure acquisition.
5. Confirm `dds_influx_subscriber.exe` receives pressure DDS samples.
6. Confirm live console printing appears when enabled.
7. Confirm pressure rows are written to InfluxDB.
8. Disable console printing and confirm the subscriber can still run.
